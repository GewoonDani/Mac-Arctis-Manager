# Architecture

Target macOS 14+ on Apple Silicon. IOKit HID and the diagnostic share a read-only Swift component. The SwiftUI menu bar app owns device selection, settings and reconnection. A C audio engine owns the realtime callbacks. System audio defaults remain under user control.

Apple recommends a user-space CoreAudio AudioServerPlugIn for virtual endpoints. An aggregate device combines existing streams, and process taps capture existing app streams. Neither creates two independent app-selectable destinations. AudioDriverKit is designed for hardware drivers. [Apple virtual driver sample](https://developer.apple.com/documentation/coreaudio/creating-an-audio-server-driver-plug-in). [Apple AudioDriverKit guidance](https://developer.apple.com/documentation/audiodriverkit/creating-an-audio-device-driver).

Published [LoopCraft](https://github.com/KerpoOrg/loopcraft) implementation documentation describes separate Rust HAL, timestamp ring, daemon and SwiftUI editor components. Its dynamic mixer and protocol are broader than a two-output bridge and its GPLv3+ distribution includes additional notices. [Splitwave](https://github.com/Horuse/Splitwave) documents a libASPL-based HAL driver with a Rust engine, Core Audio and ScreenCaptureKit adapters, and a Tauri interface. [Splitwave's driver source](https://github.com/Horuse/Splitwave/blob/main/src-tauri/native/virtual_driver/SplitAudioDriver.cpp) confirms one ring per device, separate Float32 input and output streams and dynamic device reconciliation from a system-wide plist. Its [build script](https://github.com/Horuse/Splitwave/blob/main/src-tauri/build.rs) pins and compiles libASPL. LoopCraft's driver source was unavailable through remote retrieval, so its internals beyond the published implementation documentation remain unverified. [BlackHole's C implementation](https://github.com/ExistentialAudio/BlackHole/blob/master/BlackHole/BlackHole.c) confirms the HAL WriteMix-to-ReadInput timestamped loopback model and fixed object IDs. Its current GPLv3 source and separate branding terms require care when distributing renamed forks. libASPL is an option for larger devices and depends on a C++ build. This project uses original fixed-layout C code and SDK APIs, with no external runtime or vendored driver.

Each virtual device is a stereo 48 kHz HAL loopback with dedicated output and monitor input streams. Audio clients write to the output and CoreAudio delivers the mix to the plug-in. Each monitor reads only its own ring. The app reads both monitors over the documented HAL interface, with no custom file sharing or privileged process. The monitor inputs may appear in input selectors. Select the physical Arctis microphone in voice apps. macOS can require microphone permission for the two monitors.

The mixer uses three HAL output Audio Units (AUHAL). Two input-only units retrieve the virtual monitors at their native rate. One output-only unit uses the selected physical device, converts the client-side Float32 PCM layout when necessary, and excludes physical microphone input. The C callbacks communicate through independent fixed-capacity single-producer/single-consumer queues. Output drives linear resampling with a bounded occupancy-based correction for USB clock drift. Each input re-primes independently after underruns. A shared stereo peak limiter prevents output from exceeding full scale. Gains approach new targets over a roughly 15 ms time constant. A center balance requests unity on both channels before limiting. [Apple AUHAL technical note](https://developer.apple.com/library/archive/technotes/tn2091/).

The virtual devices use fixed stereo Float32 at 48 kHz. HAL negotiates app-side conversion. The monitor path targets mono or stereo playback with typical 44.1 and 48 kHz USB formats. Larger sound interfaces use the first stereo pair accepted by AUHAL. Current buffer policy favors bounded latency over preserving stale samples. The online app checks route identity, nominal rate and callback progress once per second, reopening on changes or stalls. A selected external device remains selected after unplugging and resumes when its UID returns.

The plug-in loads in coreaudiod, while the menu bar app is a user process. The only persistent settings are the manual slider, output UID, optional user calibration file and system-managed login registration. Logs describe state transitions using the `org.macarctis.manager` subsystem. The app uses public HAL calls for transport and performs no hardware-report writes.
